# 预设与动态上下文设计

[English](README.md)

### 原则

预设采用明确分层。稳定身份放在精简的基础人格中；话题相关事实放在资料卡中；
对话记忆放在压缩摘要中。如果把所有事实都重复塞进永久 system prompt，不仅浪费
上下文，还会让无关信息影响每一次回答。

`preset_spec.json` 记录准确的拼接顺序，`build_prompt.py` 使用仓库内完整卡片
给出可读的参考实现。正式运行程序在 C++ 中按照同一顺序动态完成。

### 分层

1. **基础人格：**身份、家乡、职业、对“悠游豚豚”的所有权、与男性旅行者的
   关系、语言和总体行为。这里避免堆放大量口头禅和特定情景规则。
2. **全局关系索引：**常驻的精简熟人和地区联系人列表，防止模型仅仅因为用户
   提到某个地区，就随手挑一个当地名人当作玛拉妮的熟人。
3. **角色印象卡：**由当前用户消息中的别名触发，描述玛拉妮怎样看待对方，而
   不是对方的通用百科。
4. **关系边界卡：**用户点名角色时触发，把私人相识、熟悉程度、地区和联络政策
   与公开世界知识分别处理。
5. **世界观卡：**由当前用户消息中最长的匹配词触发；具体复合词会遮蔽其中较宽泛
   的子串，最多按照 LRU 顺序保留六张。
6. **回答模式：**短回答通常一到两句；长回答除简单问候外通常四到八句。用户明确
   要求详细说明时，可以覆盖短回答模式。
7. **压缩摘要：**可信的早期对话记忆放在行为层之后，并明确标记为历史，而不是
   用户本轮的新发言。

### 隐藏草稿一致性检查

存在激活卡时，程序会用当前关系与世界观边界检查一份不展示给用户的草稿。草稿
新提到的名字还可以激活额外人物卡或关系卡。出现实质矛盾时，程序带着简短修正
要求隐藏重生成；连续两次仍失败时，改用有依据的保底回答，而不是把验证器的拒绝
信息暴露给用户。

检查器必须区分事实矛盾和正常发挥。“我不认识宵宫，不过你可以介绍我们认识”
符合边界；声称玛拉妮能联系宵宫或知道她的日程则不符合。对稻妻了解有限，也不
妨碍玛拉妮同意和旅行者一起去那里。

### 构建可检查的提示词

```bash
python presets/build_prompt.py \
  --mode short \
  --character kachina \
  --relationship yoimiya \
  --world inazuma_overview \
  --output /tmp/mualani-prompt.txt
```

这个命令用于检查和实验。正式应用会从用户文本自动激活卡片，不需要预先生成一个
巨大的固定提示词。

### 更新预设

新的稳定身份事实放入 `base/`，回答长度行为放入 `modes/`，注入格式放入
`injection/`。与具体人物或话题绑定的事实应放入完整卡片。增加新的基础规则前，
应先判断问题能否表示成关系边界、认知边界或卡片专属行为，以保持永久提示词精简。
